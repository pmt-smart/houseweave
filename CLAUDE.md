# CLAUDE.md — working notes for Claude Code

> Operational guidance for Claude Code sessions in this repository, not its documentation. To understand the project, start with the
> [README](README.md), which indexes [`docs/`](docs/).

## In one paragraph

A brain in Berry, compiled into Tasmota from our fork, runs on a Sonoff NSPanel in each room and on a Sonoff ZBBridge Pro in each area (the
Zigbee coordinator, a CC2652P); the nodes form an ESP-NOW mesh, the house, and the panels draw our own pages, generated by `libs/nspanel-sim/`.
None of it depends on Home Assistant. Details: [docs/01-overview.md](docs/01-overview.md).

## Constraints (never break them)

- **The firmware is Tasmota.** No ESPHome, no firmware of our own.
- **A panel works fully without Home Assistant.**
- **One Zigbee coordinator per area, in that area's bridge.**
- **No computer in a room.**
- **Home Assistant is an optional observer**, never a dependency.

## How to work here

- **Do not invent protocol or commands.** The screen's vocabulary, Tasmota's commands and Zigbee2Tasmota's messages come from reading their
  source (the fork in `firmware/tasmota/`, the vendored `reference/joBr99/`), never from a guess.
- **Berry**: read [docs/12-berry-notes.md](docs/12-berry-notes.md) before creating or editing a `.be` file. The brain is compiled into the
  firmware: one class per file, with its `#@ solidify:` line; nothing at the top but the class; `import` inside each function that uses the
  module; `static` members read-only. The device compiles in strict mode with globals by name: a builtin's name (`list`, `range`, `open`...) as a
  variable does not compile, and a function cannot pass 256 constants.
- **The panel's heap is the scarcest resource**, and the app's flash the other budget ([docs/03-architecture.md](docs/03-architecture.md) §6).
  Before adding a screen, a table or a view, count its bytes. Every build that changes an image's free flash records it in
  [the journal](docs/00-journal.md), in the same commit. What leaves Tasmota is decided one cut at a time.
- **Before committing code, and before anything is written to a device: `node scripts/verify.mjs`** ([docs/13-testing.md](docs/13-testing.md)).
  There is no CI; this is the gate. `--quick` takes a few minutes.
- **Behaviour that needs the real device** (the UART, the screen's handshake, physical timing, the radio) is tested on the device, over its
  console, Web UI or HTTP API ([docs/12-berry-notes.md](docs/12-berry-notes.md) §8), not simulated. **Pure logic in a `.be`** is tested off the
  device, in `berry/test/`.
- **`firmware/tasmota/` is our fork of Tasmota** (a submodule). The build's configuration goes in `firmware/overrides/`. Our C, a driver or a
  fix, goes on a `fix/` or `feature/` branch of the fork, stacked on the previous one and pushed to it before the commit here. A build leaves
  nothing changed in the submodule ([docs/11-build-and-flash.md](docs/11-build-and-flash.md)).
- **C deeper than configuration** (a new driver) is a self-contained patch, with a minimal hook when one is unavoidable, behind a `USE_...`
  switch, as Tasmota does. **Patches to the fork are written as if for Tasmota upstream**: standard IoT and Zigbee terms, never this project's
  jargon, and never a reference to this repository's documentation; the *why* lives in `docs/`.
- **Every code file is in English**: identifiers, comments, log messages and tests. The words a panel shows are content.
- **A comment says how the code is and why, never its history**: no dates, no "used to", no "until then", no labels of a review or a
  plan. A failure the code guards against is said as what would happen without it. History goes in [the journal](docs/00-journal.md).
- **Documentation lives only in `docs/`, in English**, following the README's conventions. Before committing it:
  `node scripts/check-doc-links.mjs` **and** `node scripts/check-doc-paths.mjs`.
- **The simulator runs the repository's Berry** on Tasmota's Berry VM in WebAssembly, with the compiled pages on an emulated Nextion
  ([docs/10-simulator-and-tft.md](docs/10-simulator-and-tft.md)): a change of behaviour is made once, in the Berry. The vectors of
  `berry/test/vectors/` are the Berry suite's: a change on purpose rewrites `draw.json` and `ui.json` with
  `node berry/test/run.mjs --update-vectors`, and the diff is the review; `store.json` is written by hand.
- **Flashing a `.tft` to a panel is the hardware owner's decision.** A session prepares everything up to the preflight and stops there.
- **Version for replication**: this repository is the source of truth applied to every room's panel and bridge.
- **Before declaring a ZBBridge Pro dead**, see its intermittent silence in [docs/02-hardware.md](docs/02-hardware.md) §2: a physical power
  cycle brings it back.
- **At the start of a session**, glance at [the journal](docs/00-journal.md): what was tried, what went wrong and why.
